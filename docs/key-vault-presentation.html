Opening script

Every production application needs sensitive configuration. The easy part is creating a password or key. The difficult part is ensuring that it does not leak into source code, container images, Kubernetes manifests, terminal history, or logs, while still making it available to the correct workload at runtime.

Ask the audience: if our application needs a database key, where should that key live, and how should the running pod obtain it?

Explain that removing a secret from the latest Git commit does not remove it from history. Container layers may retain copied values. Manifests are often copied into reviews, tickets, and CI logs.

A complete secret lifecycle includes creation, storage, distribution, consumption, rotation, revocation, audit, and recovery. A secure solution must control the lifecycle, not merely provide an encrypted storage location.

Transition: Azure Key Vault is the storage and policy center, but its value depends on identity, authorization, networking, and application integration.

Speaker notes

Explain the distinction between secrets, keys, and certificates. This implementation uses secrets only.

cosmos-key and auth-jwt-secret are highly sensitive. The Cosmos endpoint is less sensitive, but is stored in Key Vault here to demonstrate centralized configuration retrieval.

Key Vault does not authenticate human users, expose the web app, provide application DNS, replace the database, or automatically rotate every dependent credential.

Explain Azure RBAC: the deployment user may need Key Vault Secrets Officer to create values, while the application UAMI only needs Key Vault Secrets User. Contributor or Key Vault Contributor does not automatically provide secret-value access.

Architecture walkthrough

User traffic reaches a public IP and Azure Load Balancer. The Kubernetes Service maps port 80 to Next.js on pod port 3000. Next.js proxies API requests to FastAPI on localhost port 8000.

AKS pulls the application image from Docker Hub. That happens before the application starts and is independent from Key Vault access.

The pod uses namespace keyvault-demo, ServiceAccount keyvault-demo-sa, and two replicas. Workload Identity connects the ServiceAccount to a UAMI.

Key Vault supplies Cosmos credentials and JWT signing material. Cosmos database demoapp contains users partitioned by email and notes partitioned by owner.

Key Vault and Cosmos DB are managed services outside the VNet boundary. Their private endpoint network interfaces are inside the VNet, and private DNS resolves their normal hostnames to private IP addresses.

Speaker notes

The ServiceAccount is the Kubernetes identity. Its annotation contains the UAMI client ID. The deployment pod label enables Workload Identity mutation.

The OIDC issuer lets Entra ID validate tokens created by this cluster. The federated credential trusts one exact issuer, ServiceAccount subject, and audience. Changing the namespace or ServiceAccount changes the subject and breaks federation.

The UAMI is the Azure identity. Azure role assignments use its principal or object ID, while the ServiceAccount annotation references its client ID.

DefaultAzureCredential() detects the Workload Identity environment and exchanges the projected token for an Azure access token.

Compare this to a service-principal client secret: federation avoids a long-lived secret, manual rotation, and expiry monitoring.

UAMI is appropriate for AKS-to-Azure access. App Registration remains appropriate for Entra user login, redirect URIs, OAuth scopes, Graph permissions, and external application identities.

Speaker notes

This slide separates Azure workload authentication from human application authentication.

Registration: validate the user input, salt and hash the password with PBKDF2, store the user in the Cosmos users container, retrieve auth-jwt-secret, and sign a JWT.

Sign-in: find the user through the email partition, verify the password hash, then issue a JWT.

Authenticated note requests send Authorization: Bearer <JWT>. FastAPI verifies the signature, identifies the user, and writes notes under that owner.

The pod separately calls Key Vault with an Azure access token representing the UAMI. Key Vault checks the Key Vault Secrets User role before returning a value.

Production limitation: the application uses the powerful Cosmos account key. A stronger design uses UAMI plus Cosmos DB data-plane RBAC and removes the account key entirely.

Speaker notes

The manifest stores the Key Vault URL, secret names, database names and container names. It does not store the Cosmos key, JWT secret value or an Azure client secret.

Private endpoints create private network interfaces in the VNet. Private DNS resolves the normal Azure hostnames to the private IP addresses.

A common failure is creating a private endpoint without linking its private DNS zone to the AKS VNet. RBAC may be correct while the pod still receives DNS failures or timeouts.

The AKS API server may also be private. Regular Cloud Shell cannot necessarily reach it. kubectl must run from VNet-injected Cloud Shell, a connected VM, VPN/ExpressRoute, or another approved network.

Application DNS is separate. A future domain can point to the LoadBalancer or ingress IP. App Registration is not required for DNS, but may be needed later for Entra login redirect URIs.

Speaker notes

Each secret update creates a new version. The application requests by name and receives the current version.

This implementation caches some clients and values. Updating Key Vault does not guarantee that both replicas immediately reload the new value. Rotation must include a controlled rollout or refresh strategy.

Changing an HMAC JWT signing secret immediately invalidates old tokens. A mature design can support overlapping keys, key IDs, or delegate authentication to an identity provider.

Soft delete permits recovery during retention. Purge protection prevents permanent deletion until the retention period expires.

Enable diagnostic settings and send logs to Log Analytics or the approved destination. Alert on denied access, secret deletion, purge attempts, role changes and federated credential changes.

Troubleshoot in layers: pod state, ServiceAccount, label, federation, Azure token, RBAC, DNS, network, secret existence, then dependent service authentication.

Closing script

Summarize what the project proves: secrets are not hardcoded, the pod does not contain an Azure client secret, one workload identity receives least-privilege access, and private networking reduces service exposure.

Production improvements include Cosmos DB data-plane RBAC, TLS ingress, custom DNS, automated rotation, diagnostics, Azure Policy, separate vaults and identities per environment, pod security, network policies, immutable image digests and CI/CD approval.

Explain alternatives: the Secrets Store CSI Driver can mount Key Vault objects as files, and External Secrets Operator can synchronize external values into Kubernetes. Both introduce different operational and security tradeoffs.

Entra ID human login would use an App Registration with redirect URIs, OAuth/OIDC configuration, scopes and consent.

Close with: the strongest result is not merely encrypted storage. The workload proves who it is, receives only the access it needs, reaches the vault through an approved network path, and leaves an auditable control trail.
